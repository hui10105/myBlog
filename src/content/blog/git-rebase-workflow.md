功能分支开了两周，评审时同事只留了一句话：这十七个提交我看不出你想讲什么故事。点开历史，里面躺着 `wip`、`fix`、`fix again`、`先这样`、`改回上一版`，中间还有一次把误删的文件从垃圾堆里捞回来的提交。代码本身没问题，但没人能从中读出这个功能的演进逻辑。

那天下午我花了一个小时做了一次完整的交互式 rebase。这篇记录它。

## 动手之前先做备份

rebase 会重写提交，出错时 `git rebase --abort` 能救你，但前提是你还没把中间状态搅乱。我更习惯在动手前留一个分支作为锚点：

```bash
# 确认工作区干净，有未提交改动时先 stash 或提交
git status

# 建一个备份分支：整理失败时可以直接切回来重来
git switch -c backup/feature-export

# 回到功能分支，重写最近十七个提交
git switch feature/export
git rebase -i HEAD~17
```

备份分支的代价只是一行命令，回报是「万一整理乱了，我不用从零再写一遍」。这条习惯来自一次真实事故：我在 rebase 过程中误用了 `--skip`，跳过了几个本该保留的修改，直到两天后测试才发现某个校验逻辑整段消失。

## 十七个提交怎么变成五个

交互式 rebase 打开编辑器后，我按「一个提交讲一件事」的原则重新归类。`pick` 保留、`squash` 合并并保留信息、`fixup` 合并但丢弃信息、`reword` 只改信息：

| 原提交 | 处理方式 | 整理后的结果 |
| --- | --- | --- |
| wip | 与后续三个打包 | 引入导出配置与默认值 |
| fix / fix again | fixup | 归入上一条，不单独出现 |
| 抽出格式转换函数 | pick + reword | 抽出列格式转换函数并加测试 |
| 改了缩进 | fixup | 合并进格式化那一条 |
| 补一行注释 | fixup | 合并进对应实现提交 |

整理完只剩五条提交，读起来是一条直线：加配置、抽函数、接上接口、补测试、更新文档。过程中最有用的两个参数是 `git rebase -i --autosquash` 和 `git commit --fixup=<hash>` —— 写代码时随手把修补提交标记成 fixup，整理阶段一次自动归位，省掉了大半手工排序。

## 冲突与推送

rebase 的冲突可能反复出现：同一个文件在不同提交里被多次修改，每合并一次就冲突一次。`git rerere` 能记住我处理过的冲突解法，遇到相同冲突自动套用：

```bash
# 开启冲突复用，一次开启长期有效
git config --global rerere.enabled true

# 冲突出现后：解决、暂存、继续
git add src/export/csv.ts
git rebase --continue

# 先看一眼远端有没有新提交，再决定怎么推
git fetch origin
git push --force-with-lease origin feature/export
```

整理完之后我还会做一次对照检查：`git range-diff backup/feature/export feature/export` 会按提交逐条列出两个分支的差异。如果某条提交被我误删、或者 merge 时悄悄丢了一行代码，这里一眼就能看出来。这比看全量 diff 直观得多，也是我确认整理没有改变功能行为的最后一道关口。

推送这一步我刻意从 `--force` 换成了 `--force-with-lease`。区别很实在：`--force` 会无条件覆盖远端，而 `--force-with-lease` 会先确认远端的提交是否还停留在我上次看到的位置。如果同事在我整理期间往这个分支推了新东西，命令会直接被我拒绝掉，而不是把人家的提交抹掉。

## 哪些情况不该 rebase

不是所有历史都适合重写。我给自己定了三条红线：

1. 分支已经合进主干，就不再重写这段历史，直接追加新提交。
2. 有别人正在基于这个分支开发时，先沟通再动手，或者改用合并提交。
3. 只为了「看起来整齐」而重写一个已经稳定运行数月的分支，不值得。

判断标准其实只有一句：这段历史还有没有人在读、在建。如果它是别人正在依赖的基底，它就是公共契约，不能随手改写。

## 小结

rebase 不是美化工具，它的真实用途是让提交粒度对齐思考粒度。整理之后的五个提交，让评审的人在十分钟内看懂了整个功能，也让我自己在半年后回看时能定位到具体是哪一步引入了问题。

下一步我打算把提交信息的模板固定下来：一行说清做了什么，正文写清为什么这么选。这样大部分提交在写下的那一刻就已经足够干净，需要 rebase 收拾的场合会越来越少。
