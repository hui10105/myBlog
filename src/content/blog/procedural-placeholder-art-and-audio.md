「先学美术」是独立开发者最常掉进去的坑。不是因为美术不重要，而是因为**你会在还不知道游戏好不好玩的时候，就先把几个月花在画图上**——而那个游戏很可能做完之后根本不好玩。

这个项目换了个顺序：先用程序化生成的占位资源做一个能完整玩的游戏，**等玩法验证通过之后再考虑换正式美术**。

结果比想象中好：35 张精灵、16 个音效，加起来的"素材文件"是两个 `.gd` 脚本。游戏能上架 Steam，而且**零版权风险**——因为在法律意义上，这些资源是我自己生成的，不是下载的。

这篇文章完整讲清这两件事怎么做。都是新手能直接抄的。

## 一、精灵图：把美术变成纯文本

### 核心想法

一张像素画，本质上就是一个二维的颜色网格。所以我们可以用一个二维的字符数组来描述它：

- 每个字符代表一个像素
- 字符在「调色板」里查到对应颜色
- `.` 表示透明

```gdscript
"jiangshi": {
    "pivot": Vector2i(8, 15),
    "rows": [
        "................",
        ".......RR.......",
        "....KKKKKKKK....",
        "....KHHHHHHK....",
        "...KPPPEEPPPK...",
        "...KPPPEEPPPK...",
        "...KPPPPPPPPK...",
        "....KPPPPPPK....",
        "KKKKKKKKKKKKKKKK",
        "KPPPPBKKKKBPPPPK",
        "..KKKBBBBBBKKK..",
        "....KBBBBBBK....",
        "....KBBMMBBK....",
        "....KBBBBBBK....",
        "....KBBKKBBK....",
        "....KKK..KKK....",
    ],
},
```

上面这个是「跳尸」——基础僵尸。如果把它渲染出来，你会看到：一顶清朝官帽（`HHHH`）、惨白的尸身（`P`）、额头上贴着一张黄符（`EE`）、以及**水平伸出去的两条手臂**（第 9 行那一条横贯整行的 `KKKK...`）。

「双臂平伸、双脚并跳」是僵尸片的招牌姿势，所以它必须进剪影——这是设计层面的决定，后面会再讲。

### 调色板怎么设计

调色板是一个字符到颜色的字典。这个项目用了 24 个字符：

```gdscript
const PALETTE: Dictionary = {
    ".": Color(0, 0, 0, 0),          # 透明
    "K": Color("101014"),            # 墨黑——所有角色的描边色
    "H": Color("26262e"),            # 道冠/官帽 黑
    "S": Color("f0c8a0"),            # 皮肤
    "W": Color("e8e4d8"),            # 白胡须 / 白纸
    "Y": Color("e0b84a"),            # 杏黄道袍
    "R": Color("b83a2e"),            # 朱砂红
    "B": Color("2a3a5a"),            # 藏青官服（僵尸）
    "P": Color("b8c4a0"),            # 尸身惨白
    "E": Color("f2e6b0"),            # 符纸黄
    "V": Color("b07ad8"),            # 幽紫（鬼怪）
    # ... 还有暗部色、石头色、玉石色等
}
```

设计调色板时有三个经验值得抄：

**1. 给每种颜色配一个「暗部」版本。** 比如杏黄道袍是 `Y`，暗部就是 `y`（同一个色相、更暗）。有暗部才能做出"衣服的褶皱"和"光影方向"，否则整个角色是平的。

**2. 所有角色共用同一种描边色。** 这是最重要的一条。`K` 这个墨黑被所有精灵用来描边，于是哪怕颜色和形状都不同，一堆小人在暗色背景上也有统一的"存在感"。**统一轮廓比配色更能提升可辨认度。**

**3. 颜色数量控制在 20 个左右。** 太少不够用，太多你就记不住了——而"凭记忆写字符画"是这个方法能快速迭代的关键。

### 锚点（pivot）：为什么需要它

每个精灵还带一个 `pivot`，指的是「这个精灵的哪一点对应游戏世界里的坐标」。

```gdscript
"pivot": Vector2i(8, 15),
```

`(8, 15)` 表示一个 16x16 精灵的**底边中点**——也就是**脚底**。这样设定之后，角色站在地面上时，它的 `global_position` 就等于脚底位置，符合直觉。

后面的好处很大：

- 设置 `Sprite2D.offset = -pivot`，贴图就自动对齐好了
- 影子画在 `position (0, 0)`，就在脚底
- 判定半径可以直接从 `pivot.x` 推导（见下文）

**如果你把锚点设成左上角，你会写出一堆 `+ Vector2(0, -16)` 之类的偏移修正，而这些修正会在改贴图尺寸时全部失效。**

### 从贴图推导数据，而不是多配一个字段

碰撞判定需要一个身体半径。直觉做法是给每种敌人手配一个 `body_radius` 字段，但那样会出现「改了图忘了改半径」的问题。

这个项目直接从贴图推导：

```gdscript
var half_width: float = PixelArt.get_pivot(stats.sprite_id).x * stats.scale_mult
body_radius = maxf(2.5, half_width * 0.7)
```

`pivot.x` 正好是贴图宽度的一半，乘上缩放就是显示宽度的一半。

**凡是能从已有数据推导出来的，就不要新增字段。** 少一个字段就少一处可能不一致的地方。

### 合成贴图的代码（就十几行）

```gdscript
func _build_sprite(id: String) -> ImageTexture:
    var def: Dictionary = SPRITES[id]
    var rows: Array = def["rows"]
    var height: int = rows.size()
    var width: int = String(rows[0]).length()

    # 校验：字符画必须是矩形。这是新手最容易犯的错（少打一个点）。
    for i: int in height:
        var line: String = String(rows[i])
        if line.length() != width:
            push_error("精灵 '%s' 第 %d 行长度为 %d，应为 %d" % [id, i, line.length(), width])
            return _make_solid(Vector2i(width, height), Color.MAGENTA)

    var img: Image = Image.create(width, height, false, Image.FORMAT_RGBA8)
    for y: int in height:
        var line: String = String(rows[y])
        for x: int in width:
            var ch: String = line[x]
            if not PALETTE.has(ch):
                push_error("精灵 '%s' 第 %d 行第 %d 列出现未知字符 '%s'" % [id, y, x, ch])
                continue
            img.set_pixel(x, y, PALETTE[ch])

    _cache[id] = ImageTexture.create_from_image(img)
    return _cache[id]
```

两个细节值得注意：

**一、字符画必须校验是不是矩形。** 少打一个点就会让整张图错位，而"错位"这种问题肉眼很难定位到具体是哪一行。提前报错成本几乎为零。

**二、未知字符要报错，而不是静默跳过。** 打错一个字母（比如把小写的 `y` 打成 `v`）会出现一个透明像素，你根本看不出来。

### 启动时全部构建一次

```gdscript
func _ready() -> void:
    for id: String in SPRITES:
        _build_sprite(id)
    print("[PixelArt] 已生成 %d 个占位精灵" % _cache.size())
```

这样一旦字符画写错，**游戏一启动就报错**，而不是等到某个怪物生成时才崩。

这是个通用原则：**把"能在启动时发现的错误"全部提到启动时。**

### 想改角色长相时

直接改字符画里的几个字符就行。不需要会画画，不需要打开任何图像软件。而且改完立刻能看到结果。

想画一个横躺着的敌人（比如「飞尸」——一个会直线冲过来的僵尸）？那就把整个身体横过来：

```
"..KKKK..............",     ← 身后拖着的破烂衣摆
".KBBBBKKKKKKKKKK....",
"KKBBBBBBBBBBBBBSSSK.",     ← 头在右边，所以它面朝右
"KBBBBBBBBBBBBBBPEPPK",     ← 中间那个 E 是发光的眼睛
".KBBBBBBBBBBBBBKKK..",
```

它的剪影「躺着的」和场上所有站立的敌人都不一样，玩家一眼就能认出来。而这一点是被自动化测试守住的（见后面关于**可辨识度**那篇文章）。

## 二、音效：把声音变成一个数字序列

### 三条规律

合成音效听起来很玄，其实只有三条规律。掌握它们，你就能自己做出九成的游戏音效：

| 要素 | 决定什么 | 例子 |
| --- | --- | --- |
| **波形** | 音色 | 正弦波=圆润、方波=电子感、噪声=打击/摩擦 |
| **频率随时间变化** | 动作感 | 升调=变强/登场、降调=衰弱/死亡 |
| **振幅包络** | 手感 | 通常是 `exp(-t × k)` 指数衰减，k 越大越"脆" |

一个具体例子——「击中敌人」的音效：

```gdscript
func _make_hit() -> AudioStreamWAV:
    var duration: float = 0.09          # 90 毫秒，很短
    var buffer: PackedFloat32Array = _new_buffer(duration)
    var rng: RandomNumberGenerator = _rng_with_seed(1004)
    for i: int in buffer.size():
        var t: float = float(i) / float(MIX_RATE)
        # 噪声 → 打击感；指数衰减很快 → 手感"脆"
        var noise: float = rng.randf_range(-1.0, 1.0)
        buffer[i] = noise * exp(-t * 60.0)
    return _to_stream(buffer)
```

读法：**用噪声（而不是正弦波）是因为打击感来自宽频内容；衰减系数 60 意味着 90 毫秒后基本归零，所以听起来是"啪"而不是"哐"。**

想让它更"闷"？把 60 改成 35。想让它更"尖"？再叠一层高频正弦。**调音色就是调数字，不需要懂音频工程。**

### 采样率为什么取 16000

常见的音效采样率是 44100 或 22050。这个项目用了 16000，理由是**实测**出来的：

> 生成全部音效是在游戏启动时同步做的，会阻塞主线程。22050Hz 下实测要 162 毫秒——在低端机上可能变成 500 毫秒的启动卡顿。降到 16000Hz 后省掉约 27%，而音质损失几乎听不出来：我们的最高频内容是进化音效的三次谐波（约 6.3kHz），16000Hz 的奈奎斯特上限是 8kHz，还有余量。

奈奎斯特定理：采样率必须高于最高频率的 2 倍，否则会失真。16000Hz 能还原的最高频率是 8000Hz，而我们的内容上限是 6300Hz——够用。

**这里的教训不是"16000 是最优解"，而是"性能预算不清的地方，先量一遍再决定优化哪里"。** 我们本来以为瓶颈在每帧的播放逻辑上，一量才发现全在启动时的合成。

### 中式恐怖氛围：五声音阶

音阶的选择比合成技术更影响氛围。这个项目用的是**中式五声音阶（宫商角徵羽）**：

```gdscript
const PENTATONIC: Array[float] = [1.0, 9.0 / 8.0, 5.0 / 4.0, 3.0 / 2.0, 5.0 / 3.0]
```

它的频率比是「大二度、大三度、纯五度、大六度」，没有西方大小调那种明确的和声倾向，听感更东方、更缥缈、更不安。

**同样的合成技术，换成大调音阶就立刻变成"欢乐的冒险游戏"了。** 音阶是氛围的第一杠杆，比加混响、加失真都有效。

升级音效就是这么做的——取五声音阶的几个音依次升高，形成"往上走"的感觉：

```gdscript
# 升级音：三个音依次升高，用五声音阶所以听起来"东方"
var notes: Array[float] = [PENTATONIC[0], PENTATONIC[2], PENTATONIC[4]]
```

### 必须做首尾淡入淡出（否则有爆音）

这是新手做程序化音效最容易忽略、又最影响质感的一点。

如果一段音频结束时振幅还不为零（比如 0.11），播放停止的那一刻，扬声器振膜会从位移状态瞬间弹回零点，**听感上就是一声「咔」**。音效密集播放时尤其明显，玩家会觉得「音效很劣质」，但通常说不出哪里不对。

修法是在**唯一的出口**统一处理：

```gdscript
const FADE_IN_SECONDS: float = 0.003      # 3 毫秒
const FADE_OUT_SECONDS: float = 0.008     # 8 毫秒

func _to_stream(buffer: PackedFloat32Array, loop: bool = false) -> AudioStreamWAV:
    if not loop:
        _apply_fade(buffer)
    # ... 转成 16bit PCM 字节
```

两个细节：

- **3 毫秒淡入几乎听不出来。** 打击音的「脆」来自前 50 毫秒的包络形状，不会被 3 毫秒的淡入削弱。
- **循环音效必须跳过这个处理。** 淡入淡出会破坏循环点的连续性，反而制造出「每循环一圈响一次」的咔哒声。所以 `loop = true` 时不施加。

**凡是「所有音效都需要的处理」，就该放在唯一的出口处**——而不是在 16 个音效函数里各写一遍，然后漏掉两个。

### 独立随机源：一个会让测试「有时候对有时候不对」的坑

噪声类音效需要随机数。这里有一条硬规矩：

```gdscript
## 绝对不能用全局的 randf()
var _rng: RandomNumberGenerator = RandomNumberGenerator.new()
```

原因是：

1. 生成音效会消耗**全局随机流**，把游戏逻辑的随机序列整体错位。这个项目所有测试都用固定随机种子来保证可复现——**音效生成会直接毁掉这件事。**
2. 音效生成顺序一变（比如你加了一个新音效），整个游戏的随机结果就跟着变，之前测出来的基准数据全废。

**这个坑非常隐蔽**：你会看到测试"有时候对有时候不对"，而完全想不到是音效引起的。所以规则是：**任何非游戏逻辑的随机（音效、装饰物、粒子）都必须用自己的 `RandomNumberGenerator` 实例。**

### 16 个音效的形状速查

这套规律可以直接抄：

| 音效 | 波形 | 包络 | 频率处理 |
| --- | --- | --- | --- |
| 投剑 | 噪声 + 高音正弦 | 快衰减 | 由高到低的扫频（"嗖"） |
| 撒米 | 平滑后的噪声 | 中速衰减 | 无（宽带噪声） |
| 击中 | 纯噪声 | 极快衰减（k=60） | 无 |
| 敌人死亡 | 噪声 + 低频方波 | 慢衰减 | 明显下降（"倒下"） |
| 玩家受伤 | 低频方波 | 中速 | 下降（不祥） |
| 拾取经验 | 短正弦 | 极快 | 上升（清脆） |
| 升级 | 三个五声音阶正弦叠加 | 中速 | 依次升高 |
| 武器进化 | 多层谐波 | 长衰减 | 上升 + 尾音 |
| 落雷 | 宽带噪声 | 极快 + 尾音 | 无 |
| Boss 登场 | 低频 + 噪声 | 长 | 缓慢上升（压迫感） |
| 环境音垫 | 4 个低频分音 + LFO 调制 | 循环 | 无（靠 LFO 呼吸） |

**看这张表的方法**：升调 = 变强/好事，降调 = 衰弱/坏事。这是一条跨文化都成立的听觉直觉，用好了比任何音效素材都通用。

## 三、换成正式美术和音效时要改哪里

这是"程序化占位"这个策略最关键的设计目标：**换正式资源时，游戏逻辑一行都不用动。**

```gdscript
# 现在（占位）
PixelArt.get_texture(id)              # 运行时合成
AudioSynth.get_stream(id)             # 运行时合成

# 以后（正式资源）
load("res://art/sprites/%s.png" % id)
load("res://art/audio/%s.wav" % id)
```

因为所有代码都是通过**这两个唯一的入口**拿资源的，所以替换只发生在这两个函数里。

**这是"占位资源"能成立的前提。** 如果你让每处代码各自去 `load()` 一个路径，那"以后换正式资源"就变成了全项目搜索替换——那才是真正做不完的活。

## 小结

| 维度 | 数字 |
| --- | --- |
| 精灵 | 35 张，全部由字符画在启动时合成 |
| 音效 | 16 个，全部由波形合成（PCM 16bit 单声道 16kHz） |
| 素材文件数 | 0 |
| 版权风险 | 0（100% 原创生成） |
| 换正式资源的改动点 | 2 个函数 |

从零开始复刻这套东西的顺序，我建议是这样：

1. **先做静态的一个精灵**：硬编码一个 8x8 的字符画，写出 `_build_sprite`，让它在屏幕上显示出来。这一步大概 30 行代码。
2. **加调色板的暗部色和统一描边色**，画一个"看得过去"的小人。
3. **做合成音效**：先只做一个「击中」，用噪声 + 指数衰减。听到声音那一刻你会立刻明白这套方法的威力。
4. **把入口收成一个函数**（`get_texture` / `get_stream`），这是为将来的正式资源留门。
5. **最后才画更多内容**——不要在第 2 步就停下来雕琢一个精灵，那时候你还不知道游戏好不好玩。

最后一句是最重要的：**这套方法的全部价值，就是让你在"还不知道好不好玩"的阶段，不必把时间花在画图上。**
