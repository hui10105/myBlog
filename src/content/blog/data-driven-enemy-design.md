做敌人系统时，新手最常见的路径是这样的：先做一只僵尸，再做一个「更厉害的僵尸」（血量 ×2），然后是「很厉害的僵尸」（血量 ×4、颜色不同）。做完五六种之后发现，**它们玩起来完全一样**，只是需要多打几下。

游戏于是变成了忍耐比赛。

这篇文章讲一个更好用的思路。它不需要你会写复杂 AI，只需要你换一个提问方式。

## 换个提问：它否定了哪一种偷懒策略

先接受一个前提：**玩家一定会找到最省力的打法，然后一直用它。**

这不是玩家偷懒，这是人的天性。类幸存者游戏里最典型的万能解是「一直往前跑」——因为几乎所有的追击敌人都比玩家慢，所以只要一直跑就永远安全。

那么一个好敌人的定义就很清楚了：

> **它的存在意义，是让玩家刚才学会的那个省力打法失效。**

于是分类标准不再是「血量多少」，而是「它否定了什么」。按这个标准看这个项目的 13 种敌人：

| 敌人 | 出场 | 血 / 速 | 它否定什么 |
| --- | --- | --- | --- |
| 纸人 | 0 秒 | 6 / 44 | —（开场耗材，让玩家熟悉操作） |
| 跳尸 | 20 秒 | 14 / 24 | —（标准敌人，学走位） |
| **飞尸** | **45 秒** | 16 / **96** | **「一直往前跑就永远安全」** |
| 鬼火 | 55 秒 | 9 / 50 | 「站着不动硬扛」 |
| **女鬼** | **75 秒** | 22 / 32 | **「龟缩在角落等它过来」** |
| 纸扎童 | 100 秒 | 4 / 58 | 「一次一发、慢慢点」 |
| **血尸** | **120 秒** | 26 / 38 | **「贴脸无脑清场」** |
| **镜中鬼** | **130 秒** | 20 / **135** | **「一直跑就能甩掉所有敌人」** |
| 黑僵 | 140 秒 | 60 / 21 | 「靠击退把敌人推在门外」 |
| **棺中客** | **150 秒** | 70 / 46 | **「低头直线穿场、不看路」** |
| **养尸人** | **160 秒** | 90 / 26 | **「只管打离我最近的敌人」** |
| 尸王 | 5:00 | 1800 / 17 | Boss：召唤 4 个纸人 |
| 旱魃 | 11:00 | 4600 / 22 | Boss：召唤 5 个跳尸 |

加粗的那六个是「反万能解」敌人。它们的存在不是为了提供数值压力，而是为了**打破玩家已经建立的舒适区**。

## 逐个拆解：它们各自怎么工作

### 飞尸：治「一直跑」

速度是玩家基础速度（78）的 1.23 倍，比玩家快。

如果只是"更快地追人"，那它只是让玩家跑得更紧张——但玩家还是只需要一直跑。所以关键在于它的移动方式：

```gdscript
# 出生时就锁定方向，之后再也不修正
if stats.movement_mode == "charge":
    var to_target: Vector2 = target.global_position - global_position
    _charge_direction = to_target.normalized() if to_target.length_squared() > 0.0001 else Vector2.RIGHT
```

**它只冲一次，不会转弯。**

于是玩家的应对就变得很具体：正面对冲必死，但**横向一让就躲开**。考验的是「什么时候变向」，不是「跑多快」。

而且它必须设一个存活时间，否则冲过玩家之后会永远在屏幕外飞：

```gdscript
@export var lifetime: float = 0.0    # 冲锋型必须配它
```

**一个"冲出去就不回来"的敌人如果不清理，会变成看不见的性能泄漏。** 这个项目的自动化测试里专门有一条断言来守它。

### 女鬼：治「龟缩」

它不追你。它停在 140 像素外放远程攻击：

```gdscript
"keep_distance": 140.0,      # 追到这么近就停下
"attack_interval": 2.4,      # 每 2.4 秒开一火
"attack_range": 200.0,
```

**「一直跑」对远程敌人完全无效**——因为它不追你。你必须**主动冲进它的射程**去处理它。

这里有个容易忽略的细节：远程攻击的初始计时必须随机化。

```gdscript
# 否则同一批生成的女鬼会「同时开火」
if stats.attack_interval > 0.0:
    _attack_timer = randf() * stats.attack_interval
```

不随机的话，玩家会突然挨到一片齐射而不是零散的几发——**难度和体验完全不同**。这个"让同类敌人的行为错开"的手法，所有 RTS 和塔防都在用。

### 养尸人：治「只打最近的」

它自己躲在 60 像素外，每 6.5 秒召唤 3 个纸扎童：

```gdscript
"summon_interval": 6.5,
"summon_count": 3,
"summon_enemy": ExtResource("纸扎童"),
"keep_distance": 60.0,
```

你打它的小兵永远打不完（而且纸扎童只有 4 点血，打起来很爽，会持续吸引你的火力）。**你必须越过一整片小兵去点杀后排。**

这个敌人引入了一个新的判断：「先清眼前的小兵，还是先杀后面的召唤者？」——这是玩家第一次要做战术优先级的选择。

### 镜中鬼：治「一直跑就能甩掉一切」

这个敌人的设计过程我单独写过一篇文章，因为**它的设计声明被实测数据推翻了**，很值得借鉴。

它的机制是追你 **1.1 秒之前**的位置，而不是现在的位置：

```gdscript
if stats.movement_mode == "mirror" and stats.mirror_delay > 0.0:
    aim = EnemyManager.history_position(stats.mirror_delay)
```

我原本以为这样能"惩罚绕圈跑"，结果实测下来直线 99 像素、绕圈 85 像素，只差 14 像素——**声明是假的**。

但它有一个真实且很有价值的性质：它是**全场唯一甩不掉的追击者**。

| 跑 25 秒直线 | 结束时离玩家 |
| --- | --- |
| 镜中鬼 | 99 像素 |
| 跳尸 | 1725 像素 |

差距 17 倍。普通追击敌人都比你慢，所以"一直跑"能永远甩掉它们；而镜中鬼的间距会稳定住。它真正惩罚的是**往回跑**——回头就是迎着它撞上去。

**这里的教训是：设计声明写进文档之前，先量一遍。** 推理听起来再顺，也可能完全错。

### 棺中客：治「不看路」

它躺在你前进的方向上，等你走进 62 像素才开盖起身。

**前面所有敌人都追在你后面**，所以"一直往前跑"永远安全。棺中客是这个规律的例外——你跑过去就是自己撞上去。

它带来一个全新的要求：**看路**。其他敌人考验你怎么动，只有它考验你**往哪动**。

实现上它只加了三个字段：

```gdscript
"movement_mode": "ambush",
"ambush_trigger_radius": 62.0,   # 玩家进到这个距离就起身
"ambush_wake_delay": 9.0,        # 躺够 9 秒也自己起身
"spawn_in_view": true,           # 刷在视野内，而不是屏幕外
```

## 加一个敌人要写多少代码

这是"数据驱动"最直接的回报。

「棺中客」这个敌人，从零到能玩，代码改动是：

1. `EnemyStats` 加三个字段（触发半径、自动起身时间、是否刷在视野内）
2. `enemy.gd` 的移动函数加一个分支
3. 生成器加一个"在视野内取点"的函数
4. 两张精灵（躺着的棺材 / 起身的立绘）
5. 一个 `.tres` 数据文件

**没有动任何已有敌人的代码，也没有改武器系统、UI、存档。**

对比一下：如果敌人的行为是硬编码在各自的脚本里，加这个敌人就要写一个新类、复制一遍追击逻辑、再处理它和已有系统的所有交互点。

**判断标准很简单：如果你的「加一种新敌人」需要复制粘贴代码，那说明行为还没被抽成数据。**

## 时间轴：让每个新敌人恰好否定上一阶段的偷懒

这是这个项目里我自己最满意的一个设计手法。把出场时间排出来看：

```
 0s  纸人           ── 学会移动
20s  跳尸           ── 学会走位
45s  飞尸           ── 学会横向闪避（"一直跑"失效）
55s  鬼火           ── 学会不能站桩
75s  女鬼           ── 学会主动进攻（"龟缩"失效）
100s 纸扎童         ── 学会范围清场
120s 血尸           ── 学会拉开距离再击杀
130s 镜中鬼         ── 发现有些东西甩不掉，必须分输出杀掉
140s 黑僵           ── 学会集中火力
150s 棺中客         ── 学会看路
160s 养尸人         ── 学会优先点杀后排
5:00 尸王           ── 第一次 Boss 高潮
```

**每一种新敌人的加入，都恰好否定了前一个阶段玩家刚学会的偷懒方式。**

这带来一个很具体的体验差异：玩家不会觉得"敌人变强了"（那只是数值膨胀，会让人疲劳），而是会觉得**"我得换个打法了"**。

这是让难度曲线"感觉合理"的关键——**难度应该来自要求的改变，而不是数字的变大。**

## 三个真实的设计陷阱

这三个都是我在这个项目里踩过、并且有数据支撑的。

### 陷阱一：把「威胁」做成了「奖励」

「血尸」死后会在 34 像素内炸出 14 点伤害。设计意图是逼玩家**在远处打死它**。

但如果这个爆炸**也能伤到其他敌人**，机制就完全反了：

> 玩家会开始**故意**把血尸引到怪堆里炸。威胁消失了，还多了一个免费清场的最优解。

所以爆炸只伤害玩家，不伤害敌人。而且伤害值（14）刻意比它活着时的接触伤害（8）高得多——**活着时它不痛不痒，死了才要命**，这样玩家的处理方式才会变成"在远处打死它"。

**设计陷阱的通用形式：任何"负面机制"如果同时对玩家有利，它就会被玩家当成工具，而不是威胁。**

这个项目里有一条自动化断言专门守它：爆炸不许伤到旁边的其他敌人。

### 陷阱二：压制型敌人的经验值给高了

这是最贵的一次错误，因为它**不报错、不崩溃、测试全绿、玩起来也"感觉没问题"**。

镜中鬼加完之后，我对比了整局数据：

| 4 分钟一局 | 不加镜中鬼 | 加了（第一版） | 变化 |
| --- | --- | --- | --- |
| 击杀 | 1159 | 1107 | ↓4% |
| 掉落经验 | 2668 | 3965 | ↑49% |
| **每击杀经验** | **2.30** | **3.58** | **↑56%** |
| **等级** | **30** | **36** | **↑20%** |
| 同屏敌人峰值 | 337 | **103** | **↓69%** |

击杀数**下降**了，经验总量却**上升**了——说明每次击杀的经验涨了 56%。

原因两个，都和「它永远待在玩家旁边」直接相关：

1. 它的 `xp_value` 配了 7（跳尸只有 3）。它把刷出来的低级杂兵**替换**掉了，等于悄悄抬高了整池的平均经验。
2. 它死在玩家脚边，经验掉落**必然被立刻捡走**，一点都不会因为漂移浪费。

结果是它变成了一台**经验提款机**：玩家 4 分钟到 36 级而不是 30 级，武器变强之后敌人几乎瞬间融化，同屏数量崩到 103——**「尸潮压境」这个核心体验被削掉了六成。**

修法：`xp_value` 7 → 3（和跳尸持平），刷新权重 1.0 → 0.45。

**规律：一个"永远在你身边"的敌人，它的经验值不能高于杂兵。** 因为它必然会死在你脚边、经验必然被全额回收。

### 陷阱三：威胁必须和外观一致

棺中客躺着的时候看起来就是路边一口棺材。玩家从上面走过去是理所当然的。

**如果这时候还有接触伤害，玩家的感受不是「我中了埋伏」，而是「这游戏在乱扣血」——差别在于：前者他会怪自己没看路，后者他会怪游戏。**

所以它出生时 `contact_damage = 0`，**开盖站起来之后才恢复**。

这个项目里有一条断言钉死它：

```gdscript
if float(coffin.get("contact_damage")) > 0.0:
    _fail("棺中客测试：躺着的棺材还能扣血（威胁和外观不一致，玩家会觉得是在乱扣血）")
```

推广开来：**任何时候，"看起来无害"和"实际有害"不一致，玩家都会认为是 bug 而不是难度。**

## 三个「反万能解」的设计思路（可以直接抄）

把上面的例子抽象出来，有这么三类：

| 类型 | 做法 | 治什么 | 为什么不能靠"改快" |
| --- | --- | --- | --- |
| **直线冲锋** | 出生锁定方向，冲一次不转弯 | 一直跑 | 改快只会变成比手速；锁定方向才能逼出横向闪避 |
| **远程放风筝** | 追到一定距离就停下开火 | 龟缩 | 改快它还是会追上来；停下才是关键 |
| **召唤** | 躲在后面不断召唤小兵 | 只打最近的 | 改快它冲上来就会被顺手清掉；躲在后面才逼出优先级选择 |
| **埋伏** | 躺在地上，等玩家靠近 | 不看路 | 改快没有意义；刷在**前方**才有意义 |

**注意这四种全是「位置题」，不是「数值题」。** 它们的难度来自「你站在哪、往哪走」，而不是「它的血有多厚」。

**这就是为什么它们不需要靠堆血量来制造压力——堆血量只会让战斗变长，不会让战斗变有意思。**

## 怎么验证你的设计真的成立

设计声明写下来了，怎么知道它是真的？**只能量。**

这个项目最终形成了一套可复用的做法：

### 一、为每个敌人的"设计意图"写一条断言

比如「镜中鬼是甩不掉的」，用模拟跑 25 秒，断言它必须留在一定距离内——而且**必须带对照组**：

```gdscript
# 光测出「99 像素」说明不了任何事——万一随便什么敌人都能做到呢？
# 所以同时模拟一只跳尸，并断言它必须被甩开 600 像素以上。
if ghost_distance > limit:
    _fail("镜中鬼测试：跑 25 秒后它离你 %.0f 像素——说好的甩不掉呢？")
if walker_distance >= 0.0 and walker_distance < 600.0:
    _fail("镜中鬼测试：对照组（跳尸）只被甩开 %.0f 像素，模拟本身可能有问题")
```

**没有对照组的验证毫无意义。** 否则你完全可能测出一个看起来不错、实际任何敌人都能做到的数字。

### 二、怀疑某个敌人破坏了平衡时，做对照实验

最省事的办法是把它**关掉**再跑一遍——把 `spawn_weight` 设成 0 就行（权重 0 表示永不刷新）。

上面"经验提款机"的结论就是这么来的。

### 三、盯总量，别盯单点

这也是那条数据表教我的：**击杀数是个会骗人的指标。**

加了棺中客之后，击杀数掉了 16%：

| 4 分钟一局 | 不加棺中客 | 加了棺中客 |
| --- | --- | --- |
| 击杀 | 1059 | 892（↓16%） |
| 掉落经验 | 2244 | 2215（≈不变） |
| **等级** | **27** | **27（不变）** |

看起来像"玩家变弱了"，但**总经验和等级一模一样**。原因是构成变化：70 血的棺中客占掉的时间比 3 血的纸人多，所以用更少的高经验击杀替换了更多的低经验击杀。

**击杀数会随敌人血量构成漂移，但它不是成长速度。** 要盯的是总经验和等级。

## 新手可以怎么练

如果你想自己练这套设计思路，我建议这个顺序：

1. **先写下一个万能解。** 让你的游戏先有一个"最省力打法"（比如"一直跑"）。没有万能解，就谈不上"否定它"。
2. **给每个新敌人写一句设计声明。** 格式固定：「它让玩家的____失效。」写不出来就说明这个敌人只是在堆数值。
3. **在数据库里加字段，而不是在脚本里加分支。** 一开始会别扭，但加第三个敌人的时候就开始回本了。
4. **给每个声明配一条可量化的断言。** 写完就故意把数字改坏，确认断言会报警——**没见过失败的断言不算断言。**
5. **加完新敌人，跑一次"关掉它"的对照实验。** 这一步能抓住所有"静默破坏平衡"的问题。

最后一条最重要。这个项目里最贵的三个问题——经验提款机、同屏人数崩塌、报表口径混乱——**全都不报错，只能靠前后对比数据发现。**
