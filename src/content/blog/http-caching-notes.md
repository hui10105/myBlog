上线十分钟后收到反馈：部分用户打开页面是白屏，刷新一下又好了。我先去看资源是否发布成功，两个文件都在；再看版本号，也是新的。真正的原因在缓存：页面入口的 HTML 被 CDN 强缓存了，用户拿到的是上一版的入口文件，里面引用的是已经随发布被清理掉的旧哈希资源，请求自然 404。

这次事故让我把 HTTP 缓存的规则从头整理了一遍。这篇是整理后的笔记。

## 强缓存与协商缓存

浏览器在发请求前会先查本地缓存。如果命中的是强缓存，请求根本不会发出去；如果命中的是协商缓存，会带上校验信息问一次服务器「这个还能用吗」，服务器答 304 就用本地副本。

| 响应头 | 行为 | 我实际用在哪里 |
| --- | --- | --- |
| `Cache-Control: public, max-age=31536000, immutable` | 强缓存，一年内不再询问 | 文件名带内容哈希的脚本与样式 |
| `Cache-Control: no-cache` | 每次回源校验，校验通过仍可用本地副本 | 页面入口 HTML |
| `Cache-Control: private, no-store` | 完全不写入缓存 | 含用户信息的接口响应 |

这里有个容易记反的地方：`no-cache` 不是「不缓存」，而是「每次都得先问过服务器」；真正的不缓存是 `no-store`。我当初把入口 HTML 写成了 `no-store`，结果每次导航都完整下载一遍 HTML，在弱网下首屏明显变慢，后来才改成 `no-cache`。

## Cache-Control 的分场景写法

按资源类型分三档，是我现在固定的策略：

```http
# 静态资源：文件名里带内容哈希，内容一变文件名就变，可以放心长缓存
Cache-Control: public, max-age=31536000, immutable

# 页面入口：保留在缓存里，但每次导航都回源校验，防止引用过期清单
Cache-Control: no-cache

# 接口响应：带用户身份，禁止 CDN 与中间代理留存
Cache-Control: private, no-store
```

`immutable` 的意义在于告诉浏览器「这个地址的内容永远不会变」，于是前进后退或者用户手动刷新时也不会再去校验。它和 `max-age` 配合才有意义：如果文件名不带哈希，长缓存就是把用户锁在旧版本上。

## 协商缓存：ETag 与 Last-Modified

协商缓存靠两个字段工作。`Last-Modified` 用文件修改时间做校验，精度只到秒，同一秒内的两次改动会被认为没变；`ETag` 用内容摘要做校验，精度更高，所以服务器同时返回两者时浏览器优先用 `ETag`。

```bash
# 观察一次协商缓存的全过程：首次请求拿到 ETag，再次请求带上 If-None-Match
curl -sI https://example.internal/app.js | grep -i etag
# 假设输出：ETag: "9f2c1a"

# 带校验信息请求，命中时服务器返回 304 且没有响应体
curl -sI -H 'If-None-Match: "9f2c1a"' https://example.internal/app.js | head -1
# 期望输出：HTTP/2 304
```

踩过的坑是压缩：源站对未压缩内容算 `ETag`，而 CDN 返回的是压缩后的内容，两边的校验值对不上，协商缓存于是每次都失效，白跑一趟。最终处理办法是让边缘节点重算 `ETag`，而不是沿用源站的值。

## 为什么「刷新一下就好了」

不同的操作触发的缓存行为差别很大，这解释了很多看起来诡异的现象：

1. 地址栏回车或点链接：走完整缓存流程，强缓存命中时不发请求。
2. 按 F5 刷新：跳过强缓存，但仍然带上校验字段，通常得到 304。
3. 按 Ctrl+F5 强制刷新：请求里带 `Cache-Control: no-cache`，直接回源拿完整响应。
4. 前进后退：优先读内存或页面缓存，这也是为什么返回上一页时数据看起来是旧的。

排查时我固定看开发者工具网络面板的尺寸列：显示 `200` 说明真实下载了；`304` 说明协商成功、用的是本地副本；`(disk cache)` 或 `(memory cache)` 说明强缓存命中，请求没有离开浏览器。去年有一次我改了配置却仍然拿到老文件，就是因为那一列写着 `memory cache`，改动压根没机会生效。

## 小结

缓存策略可以先按一句话判断：内容是否随发布而改变。会随发布改变的文件名带哈希、放心长缓存；入口文件保持可校验；带身份的数据一律不落缓存。事故的根因往往不是某个参数写错，而是把这三类资源用了同一条规则。

下一步我打算在构建流程里加一道检查：发布后自动校验入口 HTML 的响应头里存在 `no-cache`，把这类配置回归拦在发布阶段，而不是等用户来反馈白屏。
