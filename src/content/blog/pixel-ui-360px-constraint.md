像素游戏绕不开一个决定：**基础分辨率取多少。**

这个项目选了 **640×360**（16:9，正好是 1920×1080 的整数三分之一）。

好处很实在：

- 像素画放大 3 倍正好铺满 1920×1080，**每个像素都是均匀的 3×3 方块**，不会出现"某些像素比别的宽一像素"的模糊
- 640×360 对性能友好
- 复古味是这个题材需要的

但它带来一个必须在设计阶段就接受的约束。

## 「垂直空间只有 360 像素」是什么意思

Godot 的窗口拉伸配置是这样：

```ini
window/size/viewport_width=640
window/size/viewport_height=360
window/stretch/mode="canvas_items"
window/stretch/aspect="expand"
```

三个设置各自的含义：

- **`canvas_items`**：整个画面按比例缩放。设成 1280×720 的窗口，所有东西放大 2 倍
- **`expand`**：窗口的宽高比和设计值不一致时，**扩展可视范围**，而不是加黑边

关键在 `expand` 这一条。它的行为是：

| 窗口 | 实际逻辑分辨率 | 说明 |
| --- | --- | --- |
| 640×360 | 640×360 | 基准 |
| 1280×720 | 640×360 | 等比放大 2 倍 |
| 1920×1080 | 640×360 | 等比放大 3 倍 |
| 1920×1200（16:10） | 640×**400** | 宽度不变，**高度多出 40** |
| 1280×1024（4:3） | 640×**512** | 宽度不变，**高度多出 152** |

看出来了吗——**在"更方"的显示器上，垂直空间会变多；但永远不会变少。**

所以 UI 布局的安全边界是：**必须以 360 像素高为准**。只要在 360 像素里放得下，在任何显示器上都放得下。

这就是那个硬上限的来源：**给 UI 加一行内容，就是从一个固定的 360 像素里再抢走十几个像素。**

## 静默破版：没有报错的坏事

这个项目有六个全屏面板：

| 面板 | 内容 |
| --- | --- |
| 主菜单 | 标题 + 开始/商店/退出 |
| 选角界面 | 4 张角色卡（每张 128×210） |
| 阴德阁 | 7 项永久强化的列表 |
| 升级面板 | 三选一，每个选项有图标 + 名称 + 描述 |
| 结算面板 | 存活时间 / 击杀 / 等级 / 阴德 / 重开按钮 |
| 暂停面板 | 音量滑块 + 设置 + 返回 |

它们大多是 `CenterContainer + VBoxContainer` 的自动布局。这种布局有一个**非常隐蔽的失效方式**：

> **内容一旦比屏幕高，它会被均匀地从上下两端挤出屏幕**——顶部标题和底部按钮同时被裁掉。

没有报错、没有警告、日志干净、游戏也不崩。你只看得到"标题怎么不见了"，而如果标题恰好是第一个被裁的元素，你甚至会以为是节点没创建出来。

**这类问题只有两种发现方式：实际渲染一遍，或者写个自动化守卫。**

## 两个真实发生过的溢出

### 一、结算面板：411 像素装进 360 像素

第一版结算面板的内容高度量出来是 **411 逻辑像素**——超了 51 个像素，上下各被挤出 25 像素左右。

修法是压缩到 **336**：

- 减少条目之间的间距
- 把「存活时间 / 击杀 / 等级」三行合成一行用分隔符排开
- 缩小标题字号

**这里的设计教训是：结算面板是一个信息密度很高的界面，而 360 像素只够放"最重要的五六行"。** 想显示更多，就只能改成分页或滚动——但那会让"一局结束看总结"这个本该痛快的一刻变得麻烦。

所以正确做法是**砍信息**，而不是加滚动。

### 二、阴德阁：加到第 8 项时放不下了

阴德阁（永久强化商店）原本是普通列表布局。加到第 7 项时还能勉强放下，但当规划里排到第 8 项时，就必然溢出。

这个面板和结算面板的性质不同：**它的内容会随着游戏内容的增加而增长**（以后还会有第 9、第 10 项强化）。所以它必须能滚动：

```gdscript
ScrollContainer
  └─ VBoxContainer
       ├─ 强化项 1
       ├─ 强化项 2
       └─ ...
```

**规律：凡是内容会随游戏进程增长的面板（商店、成就、图鉴），一开始就该用可滚动容器。**

不要等到放不下时才改结构——那时的改动会牵连交互、焦点、手柄导航等一堆东西。

## 布局测试：量了四遍才量对

因为上面两种溢出的发现成本太高，所以做了一个自动化守卫：**把六个面板逐个打开，量它们的实际内容矩形，任何超出 640×360 的判定失败。**

听起来简单，但「量出内容真正占了多大」这件事我做错了四次。这四种错误各自代表一类坑。

### v1：`get_global_rect()` — 量到上一帧的旧尺寸

第一版直接在 `_process` 里调 `get_global_rect()`。结果时灵时不灵：有时候报溢出，有时候不报。

原因是**布局还没算完**。你这一帧改了内容或打开了面板，而容器的尺寸要到布局系统跑完之后才更新。于是你量到的是上一帧的旧值。

**修法不是加个延迟，而是把测量本身挪到不同的帧去做。** 这个测试现在是跨帧的：先打开面板 → 让 Godot 跑完布局 → 下一帧再量。

```gdscript
# 阶段 1：打开所有面板
stage = Stage.LAYOUT

# 阶段 2：等两帧，让 Godot 完成一次完整的布局计算，然后量真实渲染矩形
Stage.LAYOUT:
    if _stage_frames >= 2:
        _measure_panel_layouts()
```

### v2：`get_combined_minimum_size()` — 算出离谱的假溢出

第二版想绕开布局时机问题（最小尺寸是内容自己算的，不依赖布局），结果它**会算错**。

原因很具体：面板里的描述文字是**自动换行**的标签。而在"宽度未知"的情况下，它按极窄宽度估算高度——算出 **584 像素**这种离谱数字，报了一个根本不存在的溢出。

**自动换行标签的高度取决于它有多宽。** 在宽度确定之前，任何"最小尺寸"都是猜的。

### v3：所有内容控件的并集 — 把滚出视野的行也算进去

第三版改成"遍历所有子控件，取矩形并集"。这个思路对普通面板是对的，但**在滚动列表上会假报溢出**——已经滚出视野的行仍然在节点树里，它们的矩形还在。

于是阴德阁永远报溢出，而实际显示是正常的。

### v4：分情况处理「顶层内容容器」

最终版的规则是按结构分类：

| 面板的内容容器 | 怎么量 |
| --- | --- |
| `CenterContainer` | 量它**直接子节点**的矩形（CenterContainer 会把子节点缩到最小尺寸，所以这个矩形就是内容尺寸） |
| `PanelContainer` | 用它自己的矩形（PanelContainer 会贴合内容） |
| 被拉伸铺满的 `VBoxContainer`（升级面板是这种） | 用**它的子节点的并集**（它自己被拉伸了，矩形不反映内容） |

**这四版的共同教训：测量一个自动布局系统，"取哪个节点的矩形"本身就是一个需要理解布局规则的决定。** 没有"通用的正确写法"，只有"对当前结构正确的写法"。

## 为什么只比尺寸、不比位置

这是这个测试里最后一个反直觉的点。

直觉上你会想验证"内容有没有超出屏幕边界"，那就该同时检查位置和尺寸。但实际不行：

> **无头模式下视口可能不是 640×360**，内容会被居中到另一个画布里。**位置偏移是环境造成的假象**，而"这段内容需要多少像素"是固定的。

所以断言只看尺寸：

```gdscript
# 留 2 像素容差：边框与浮点舍入不该被误判成溢出
if rect.size.y > _design_resolution.y + 2.0 or rect.size.x > _design_resolution.x + 2.0:
    _layout_overflowed.append("%s(内容需要 %.0fx%.0f，可用 %.0fx%.0f)" % [...])
```

**这是「测试环境与被测环境不同」时的一个通用处理方式：只断言那些在两种环境下都成立的性质。**

## 顺带一个坑：截图时暂停的镜头

做商店截图的时候，有两个镜头是**故意让游戏暂停**的（升级面板、阴德阁）——因为那正是玩家看到它们的时刻。

但截图脚本一开始跑不动：既不保存图片也不退出。原因是**节点默认的 `process_mode` 会让它跟着游戏一起暂停**。

```gdscript
func _ready() -> void:
    # 【必须设成 ALWAYS】否则暂停的镜头既存不了图也不会退出，
    # 表现是"跑了很久什么都没发生"
    process_mode = Node.PROCESS_MODE_ALWAYS
    get_window().size = CAPTURE_SIZE
```

另外还有一条：**截图分辨率要在运行时设 `get_window().size`，而不是用 `--resolution` 命令行参数**——后者会被项目设置里的 `window_width_override` 覆盖掉。

## 可迁移的几条原则

1. **先确定基础分辨率，再设计 UI。** 分辨率决定了垂直空间的上限，而 UI 是"从这份固定预算里分配"。
2. **对固定分辨率的设计，安全边界取最小值。** 用 `expand` 时垂直空间只增不减，所以按 360 像素设计就永远不会破版。
3. **内容会增长的面板，一开始就用滚动容器。** 等到放不下时再改结构，代价大得多。
4. **自动布局的溢出是静默的。** 写一个跨帧量真实渲染矩形的守卫测试，比每次上线前手点一遍可靠。
5. **测量自动布局要先理解布局规则。** "取哪个节点的矩形"没有通用答案。
6. **只断言在测试环境和真实环境下都成立的性质。** 比如内容需要的像素数，而不是它在屏幕上的位置。
7. **信息装不下的时候，优先砍信息，而不是加滚动。** 一个"看总结"的界面变成长列表，就失去了它的意义。

最后一条其实是设计问题而不是技术问题，但它在像素游戏里会以技术约束的形式不断出现——**这个约束的价值在于它逼你做取舍**。640×360 装不下所有你想显示的东西，所以你被迫回答"这一屏最重要的三件事是什么"。而在一个 4K 分辨率的界面里，你可以把所有东西都塞进去，然后玩家一个都记不住。
