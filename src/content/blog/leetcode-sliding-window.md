第一次做「长度最小的子数组」时，我写了嵌套的两层循环：外层枚举起点，内层枚举终点，求和一遍，取最小的满足条件者。样例全过，提交之后超时了 —— 数据规模到十万，平方级复杂度不可能过。

看题解才明白，这道题的窗口左边界根本不需要回退。从那以后，滑动窗口成了我用来处理「连续子数组 / 子串」的第一选择。

## 能不能用滑动窗口，先看单调性

滑动窗口的本质是：用两个指针框出一段连续区间，右指针负责扩张，左指针负责收缩。它成立的前提是一个单调关系 —— 右指针往前走之后，左指针不需要回头。

以「长度最小的子数组」为例，元素全是正整数。窗口右端右移，窗口和只会变大；窗口左端右移，窗口和只会变小。正因为左右移动对和的影响是单向的，我才可以在和达到目标后放心地收缩左端，并且不再回退。

反例是包含负数的版本：右移可能让和变小，此前被跳过的区间也许重新变得可行，单调性消失，这时就必须换回前缀和或者其他方法。写题时先确认这个前提，比背模板重要得多。

## 不同题目要维护的量不一样

模板骨架相似，真正需要设计的是窗口里存什么：

| 题目 | 窗口条件 | 需要维护的量 |
| --- | --- | --- |
| 长度最小的子数组 | 窗口和大于等于目标值 | 一个累加和 |
| 无重复字符的最长子串 | 窗口内无重复字符 | 每个字符最后出现的位置 |
| 最小覆盖子串 | 覆盖目标串的全部字符 | 字符计数表与已满足的种类数 |

「无重复字符的最长子串」那题我最初用 `Set` 做，收缩左边界时按 `while` 逐个删除字符，写法正确但多了一层循环。改成记录「每个字符最后出现的位置」之后，发现重复时可以直接把左指针跳到重复字符的下一位，一步到位。这个改进让我第一次体会到：维护什么量决定了代码能有多简洁。

## 一套可复用的模板

下面是我现在写在笔记里的标准形态，用「长度最小的子数组」做骨架，注释标出四个决策点：

```ts
function minSubArrayLen(target: number, nums: number[]): number {
  let left = 0;            // 窗口左边界，只会向右移动
  let sum = 0;             // 决策点一：窗口内维护的量
  let best = Infinity;

  for (let right = 0; right < nums.length; right++) {
    sum += nums[right];    // 右指针进入窗口

    // 决策点二：条件是 while 不是 if，
    // 一次扩张可能让左边界需要连续收缩多次
    while (sum >= target) {
      // 决策点三：在收缩过程中更新答案，
      // 因为此刻窗口才是满足条件的最小形态
      best = Math.min(best, right - left + 1);
      sum -= nums[left];
      left++;
    }
  }

  // 决策点四：没有满足条件的窗口时返回约定的空值
  return best === Infinity ? 0 : best;
}
```

把这四个决策点单独拎出来，是因为我踩过的坑几乎都落在这里：`while` 写成 `if` 导致答案偏大；在右指针扩张后而不是收缩完成后更新答案，导致统计到不满足条件的窗口；忘记处理空结果，`Infinity` 直接被当答案返回。

## 别停在背模板

模板能帮我少写一半代码，但它也会掩盖问题。现在做完一道滑动窗口题，我会固定回答三个问题再收工：

1. 这道题的单调性来自哪里，什么情况下会被破坏？
2. 窗口内维护的量，能不能换成更省的结构？
3. 边界情况有哪些：空数组、窗口始终不满足条件、恰好等于阈值。

这三问连同代码一起写进笔记系统，格式统一，标签固定为题型和语言。这样下次遇到同类题，我搜到的不是一段陌生代码，而是自己当时的判断过程。事实证明，三个月后再看，能看懂的是那些写清了不变量的条目，看不懂的往往是只抄了代码的条目。

## 小结

滑动窗口的关键不在双手指，而在两个问题的答案：为什么左边界可以不回头，以及窗口里到底要记住什么。把这两个问题想明白，模板只是顺手写出来的副产品。

下一步我准备按同样方式整理双指针与二分查找：先弄清各自的适用前提，再沉淀模板，最后用三问复盘固定下来。
